# Agentic Workflow 平台化重构计划

> 目标：将当前“多场景智能客服 Demo”逐步升级为“面向客服、质检、运营场景的企业任务型 Agent 工作台”。推进原则是 **小步快跑、先评估后扩展、每阶段可回滚**，不为了速度牺牲稳定性与可验证性。

## 0. 当前问题基线

当前项目具备 Streamlit 页面、多场景配置、LangChain ReAct Agent、Chroma RAG 和部分工具调用能力，但仍属于 Demo 型项目：

- `app.py` 同时承载 UI、登录、上传、会话、Agent 调用，职责过重。
- 管理员账号、外部服务 key 配置方式不安全。
- Agent 只是单轮 `invoke` 后逐字模拟流式，并非真正流式执行。
- 工具散落在 `agent_tools.py`，缺少注册、权限、超时、审计与结构化结果。
- RAG 只有基础检索与拼接，没有评测、rerank、引用、无答案判断。
- 没有单元测试、集成测试、效果评估和回归基线。

## 1. 推进原则

1. **先安全再功能**：密钥、账号、日志脱敏优先于新功能。
2. **先基线再优化**：每次 Agent/RAG 改造前先建立可复现评测集。
3. **先模块化再平台化**：先在现有 Streamlit 架构内拆层，再迁移到 FastAPI + Web 前端。
4. **可观测优先**：所有 Agent 执行、工具调用、RAG 命中都要留下结构化轨迹。
5. **人工可控**：高风险动作必须支持 human-in-the-loop 确认。

## 2. 阶段规划

### 阶段一：Demo 硬化与安全治理

目标：让现有项目可安全运行、可测试、可继续迭代。

交付：

- 新增 `.gitignore`，禁止提交 `.env`、日志、缓存、向量库产物。
- 新增 `.env.example`，只提供占位符，不提交真实密钥。
- 管理员账号、DashScope、Ark、Seed、高德 key 改为环境变量读取。
- 新增配置加载与敏感信息脱敏工具。
- 补齐 `python-dotenv`、`pytest` 等基础依赖。
- 新增基础测试：配置加载、密钥脱敏、管理员配置读取。

验收标准：

- 仓库中不出现真实 API Key。
- `python -m compileall .` 通过。
- `pytest` 基础测试通过。
- README 明确说明如何使用环境变量配置密钥。

### 阶段二：模块拆分与基础服务层

目标：降低 `app.py` 复杂度，形成可迁移到 API 的内部服务接口。

交付：

- `services/scene_service.py`：场景读取、校验、默认场景。
- `services/agent_service.py`：统一 Agent 调用入口，屏蔽 UI 细节。
- `services/knowledge_service.py`：知识库上传、去重、入库封装。
- `services/evaluation_service.py`：离线评测入口。
- 将 Streamlit 仅保留为交互层。

验收标准：

- 原有页面功能不回退。
- Agent 调用、知识库上传均可通过服务类调用。
- 新增模块有基础单元测试。

### 阶段三：评测体系与质量基线

目标：用数据衡量优化效果，避免盲目改 Prompt 或堆工具。

交付：

- `eval/datasets/*.jsonl`：按场景维护测试集。
- `eval/run_eval.py`：批量运行 Agent 回答。
- `eval/judges/ark_seed.py`：通过 Ark/Seed 模型进行自动评分。
- 输出 `eval/reports/*.md|json`：记录正确性、引用质量、拒答能力、响应耗时。

验收标准：

- 每个核心场景至少 10 条用例。
- 每次核心改造前后均可生成对比报告。
- 评测脚本不在仓库中写入真实 key。

### 阶段四：Agentic Workflow 化

目标：从“问答 Agent”升级到“任务执行 Agent”。

交付：

- 引入显式工作流：任务理解、检索、工具调用、生成、人工确认、完成。
- 工具注册中心：统一 schema、权限、超时、重试、审计。
- 执行轨迹：展示每一步输入、输出、耗时、错误。
- 高风险动作支持人工确认。

验收标准：

- 至少一个完整任务流可回放。
- 工具调用失败有可读错误与重试策略。
- 人工确认节点可暂停和继续执行。

### 阶段五：前后端分离与平台化

目标：从 Streamlit Demo 迁移到企业应用架构。

交付：

- 后端：FastAPI，提供 chat、scene、knowledge、tool、eval API。
- 前端：React/Next.js 工作台。
- 数据层：会话、任务、工具调用、评测结果持久化。
- 运营看板：命中率、解决率、失败原因、满意度、工具失败率。

验收标准：

- Streamlit 不再承载核心业务逻辑。
- API 有接口测试。
- 前端可查看 Agent 执行轨迹和评测结果。

## 3. 测试评估策略

### 工程测试

- 单元测试：配置、工具、RAG、服务层。
- 集成测试：Mock LLM、Mock VectorStore，验证完整对话链路。
- 静态检查：编译检查、依赖检查、密钥扫描。

### Agent 效果评估

- 正确性：答案是否符合知识库事实。
- 引用质量：回答是否能给出相关来源。
- 拒答能力：知识库无答案时是否避免幻觉。
- 工具调用：是否选择正确工具，参数是否合理。
- 稳定性：同一问题多次执行结果是否稳定。

### RAG 评估

- 召回命中率。
- Top-K 文档相关性。
- Chunk 切分质量。
- 无关文档干扰率。

### Ark/Seed 自动评估

Ark/Seed 配置只通过环境变量读取：

- `ARK_API_KEY`
- `ARK_BASE_URL`
- `ARK_SEED2_PRO_MODEL`
- `ARK_SEEDANCE_MODEL`
- `ARK_SEEDANCE_TASK_URL`

仓库只保留变量名和模型用途说明，不保存真实 API Key。

## 4. 近期执行顺序

1. 完成安全配置治理。
2. 补齐基础测试与编译验证。
3. 拆出服务层。
4. 建立首版评测集。
5. 再开始 Agentic Workflow 改造。

## 5. 风险控制

- 不直接大规模重写，避免功能不可用。
- 每阶段保留可运行版本。
- 每次核心改动必须通过基础测试。
- 涉及密钥、文件上传、外部调用时优先做安全检查。
